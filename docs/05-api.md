# LeadMind — the API (Phase 2)

What Phases 1 and 1b measured, served over HTTP, with the human review queue that Phase 1's
deduplication deliberately left unfinished.

Interactive reference: `make serve`, then <http://127.0.0.1:8000/docs>.
Machine-readable: [`docs/openapi.json`](openapi.json), regenerated by `make openapi`.

---

## 1. What the API is for, and what it refuses to do

Phase 1 established what is known about each lead, how reliably it is known, and what evidence
supports it. Phase 2's only job is to expose that faithfully and to let a person resolve the
73 duplicate pairs the pipeline refused to guess at.

Three constraints follow, and they shape every endpoint.

### 1.1 Nothing is smoothed over on the way out

A city is not a string — it is a string, a gazetteer match, and the confidence of that match. A
mailbox is not `valid` — it is a status that distinguishes *verified*, *proven unreachable*, and
*never measured*. A score is not a number — it is a number plus how many of its factors could
actually be evaluated.

Every one of those could have been flattened into a friendlier scalar. Every one of them would
have hidden exactly the uncertainty Phase 1 spent its time measuring, and would have made the API
a more confident liar than the pipeline behind it.

### 1.2 The only writes are review decisions

No endpoint edits a lead. Lead data comes from ingest, which is idempotent and fully reproducible
from the source workbook; if the API could mutate it, the next re-ingest would be either
destructive or a merge conflict. Neither is worth it before there is a reason.

### 1.3 A confirmed duplicate is a pointer, not a deletion

See §4. This is the single most consequential design decision in this phase.

### Explicitly out of scope

No authentication, no rate limiting, no caching. They belong in Phase 10 with the deployment
story, and a token check bolted onto a service that binds to `127.0.0.1` would be security
theatre. `leadmind serve` defaults to localhost for that reason; binding it to `0.0.0.0` today
publishes the corpus to the network.

## 2. Shape of the interface

```
GET  /healthz                              liveness — never touches the database
GET  /readyz                               readiness — database reachable + schema at head

GET  /api/v1/leads                         list, filter, sort, paginate
GET  /api/v1/leads/{id}                    one lead, its evidence and its gaps
GET  /api/v1/leads/{id}/quality            why this lead scored what it scored
GET  /api/v1/leads/{id}/provenance         the spreadsheet rows it came from

GET  /api/v1/companies                     the franchise view
GET  /api/v1/companies/{id}                one company and all its branches

GET  /api/v1/duplicates                    the review queue
GET  /api/v1/duplicates/{id}               one pair, side by side, diff pre-computed
POST /api/v1/duplicates/{id}/decision      confirm · reject · undo

GET  /api/v1/stats                         corpus counts and the reconciliation identity
GET  /api/v1/stats/quality                 score distribution and factor coverage
GET  /api/v1/stats/verification            what was measured, and how stale it is
GET  /api/v1/stats/review                  queue depth and detector precision

GET  /api/v1/meta/categories               verticals with live lead counts
GET  /api/v1/meta/locations                resolved locations with live lead counts
```

Health probes sit **outside** the version prefix on purpose: an orchestrator's liveness check
should not have to know which version of the API is deployed.

## 3. Reading leads

### 3.1 Filters

Everything below is combined with AND. Repeatable parameters are marked.

| Parameter | Notes |
|---|---|
| `q` | Substring match on name **and** on every identifier value, so pasting an email finds its lead |
| `category` ⁺ | Controlled vertical slug, not the 240 raw Facebook category strings |
| `location` ⁺ / `state` ⁺ | Gazetteer-resolved only |
| `entity_kind` ⁺ | `person` · `business` · `unknown` |
| `has` ⁺ / `missing` ⁺ | Channel presence: `email`, `phone`, `website`, `linkedin`, … |
| `min_quality` / `max_quality` | Against the current rubric unless `rubric_version` is given |
| `min_followers` / `max_followers` | The **latest** observation, not the largest |
| `owned_website` | A domain of its own, as opposed to a `linktr.ee` or a `wa.me` link |
| `mailbox_status` / `website_status` | `verified` · `unreachable` · `unknown` — see §3.4 |
| `mail_provider` | Mail host inferred from MX: `google`, `microsoft`, `zoho`, … |
| `placeholder_name` | The 6 anonymised `Advertiser 13887200` names |
| `multi_branch` | Leads whose company has more than one branch |
| `issue_code` | Leads carrying a given validation issue |
| `company_id` | |
| `include_merged` | Show leads a reviewer confirmed as duplicates. Off by default |
| `rubric_version` | Pin scoring to a specific rubric |

`sort` accepts `quality`, `followers`, `name`, `created`, `updated`, with a leading `-` for
descending. Default `-quality`.

### 3.2 Pagination is offset-based, and that is a decision

`page` and `page_size`, with a real `COUNT` for `total` — not an estimate. Two things make that
defensible here and would stop making it defensible later:

- **The corpus is 2 351 rows.** Counting is free at this size. A review UI that cannot say
  "73 pairs pending" is materially less useful than one that can.
- **Every ordering ends in a tiebreak on `id`.** Without that, two leads with the same quality
  score are free to swap places between page 1 and page 2, and a reviewer paging through the list
  sees one twice and the other never — silently, with no error anywhere. There is a unit test
  asserting the tiebreak for every sort key.

When the corpus grows past a few hundred thousand rows, `OFFSET` starts scanning and this should
become keyset pagination. It is not there today because it would be complexity bought against a
problem this dataset does not have.

`page_size` is capped at `LEADMIND_API_MAX_PAGE_SIZE` (200) and the cap is applied silently
rather than as an error — an unbounded list endpoint is a denial of service with extra steps.

### 3.3 One page costs a constant number of queries

A page of leads needs the lead rows, their identifiers, their follower observations, their
quality scores, their verification status and their issue counts. Loading those per row is the
N+1 that turns a 25-row page into 150 round trips. Everything is fetched page-first, then each
dependency resolved in one further query keyed on the page's ids.

This is asserted, not asserted-about: an integration test counts SQL statements and requires a
100-row page to cost exactly as many queries as a 25-row page. An N+1 regression does not return
wrong data — it returns exactly the right data, slowly — so no other test would catch it.

### 3.4 `null`, `unknown` and `unreachable` are three different answers

```jsonc
"verification": {
  "mailbox_status": "verified",     // measured: the domain publishes an MX record
  "mailbox_accepts_mail": true,
  "mail_provider": "google",
  "website_status": "unknown",      // there is a website; nobody has checked it
  "website_is_live": false
}
```

- **`null`** — there is nothing to check. No email address, or no website.
- **`unknown`** — there is something to check and it has not been measured. The check has not
  run, or the resolver timed out.
- **`verified` / `unreachable`** — a measurement. `unreachable` means the domain answered and
  publishes no mail exchanger; mail to this lead cannot be delivered.

A client that treats `unknown` as `unreachable` will mark good leads dead on the strength of one
bad afternoon of DNS — and the result is cached, so it stays wrong. Keeping the three apart is
the reason `VerificationOut` has its own construction path and its own unit tests rather than
being serialised straight off the model.

### 3.5 `GET /leads/{id}/quality` reads; it does not recompute

Every factor's value, weight, contribution and reason was persisted at scoring time along with
the rubric version that produced it. This endpoint returns that record.

Recomputing would answer a subtly different question — what the *current* rubric would say — and
would make every old score unexplainable the day the rubric changes. Which it will: v1.0 → v1.1
already happened when Phase 1b's measurements arrived.

```jsonc
{
  "score": 73.91,
  "rubric_version": "1.1",
  "base_score": 73.91,
  "penalty_applied": 0.0,
  "factors_evaluated": 10,
  "factors_total": 11,
  "weight_available": 90.0,        // the unmeasurable factor's weight is not in here
  "factors": [
    { "name": "website_live", "value": null, "weight": 10.0, "contribution": 0.0,
      "measured": false, "reason": "website liveness not verified yet" },
    { "name": "owned_website", "value": 1.0, "weight": 14.0, "contribution": 14.0,
      "measured": true, "reason": "owned domain pumotechnovation.com" }
  ]
}
```

`website_live` scores `null`, not `0`. Scoring it zero would punish the lead for work the
operator has not done yet; scoring it `0.5` would invent a measurement. It drops out of both
numerator and denominator, and `weight_available` records that it did.

## 4. The review queue

### 4.1 What is in it, and why it is not empty

Phase 1 auto-merged 169 pairs on exact identity keys — same email, same phone, same Facebook URL.
It queued everything weaker and merged none of it:

| Method | Pairs | What it usually means |
|---|---:|---|
| `shared_website` | 48 | Often a franchise. Five Pumo Technovation branches share one domain |
| `fuzzy_name` | 25 | A hypothesis. `rapidfuzz token_set_ratio ≥ 92` |

Deduplicating on a shared website deletes four real prospects and looks correct doing it.

### 4.2 Both leads are embedded, and the diff is pre-computed

A reviewer who has to fetch two more URLs per row to see what they are deciding will not review
anything. Each queue item carries both `LeadSummary` objects and a `comparison` array:

```jsonc
"comparison": [
  { "field": "company_domain", "a": "bostoninstituteofanalytics.org",
    "b": "bostoninstituteofanalytics.org", "agrees": true },
  { "field": "email", "a": "bia.whitetown@…", "b": "connect@…", "agrees": false },
  { "field": "location", "a": "Puducherry", "b": "Mumbai", "agrees": false }
]
```

`agrees` is `null` when the field is missing on at least one side. A missing field is not a
disagreement, and rendering it as one trains reviewers to ignore the column.

Rendering two records and leaving the diff to the eye is how franchises get merged at 2am.

### 4.3 Confirming links; it never deletes

```http
POST /api/v1/duplicates/{id}/decision
{ "decision": "confirmed_duplicate", "reviewer": "ameen", "note": "same business" }
```

This sets `leads.merged_into_id` on the loser and **touches nothing else**. Identifiers, follower
observations, provenance rows and validation issues all stay exactly where they were. The lead
disappears from listings, remains fetchable at its own URL with a `merged` block, and reappears
under `?include_merged=true`.

The alternative — deleting the loser and re-parenting its children — is irreversible, and it
breaks the reconciliation identity that is the only proof ingestion worked. A reviewer is a
fallible input like any other. The 169 exact merges were applied automatically precisely because
they were the only ones certain enough not to need an undo.

**Survivor selection.** Pass `survivor_id` to choose, or let the default pick the better-evidenced
lead: higher quality score, then more identifiers, then the earlier row, then id order. The last
tiebreak exists so the same decision produces the same database on two machines.

**Concurrency.** The candidate and both leads are locked `FOR UPDATE` for the duration. Two
reviewers opening the same pair is normal; two of them read-modify-writing `merged_into_id`
simultaneously is a race, and this is where it would happen.

**Conflicts.** Merging a lead that already points at a *different* survivor returns `409`. The
reviewer is told to undo the earlier decision rather than having it silently overwritten, because
an overwrite strands the first survivor's evidence.

**Chains.** If the chosen survivor is itself merged, the merge follows to the root, keeping the
pointer depth at one. A cycle guard bounds the walk: the database forbids self-merges but not an
A→B→A pair written by two racing requests, and an unbounded loop would hang the request rather
than fail it.

### 4.4 Undo is a decision, not an exception

```http
{ "decision": "pending", "reviewer": "ameen", "note": "not the same business" }
```

Reverses the merge and returns the pair to the queue. A review tool without an undo trains its
reviewers to hesitate, which produces worse decisions than a wrong one that can be corrected.

One subtlety: a pair can be flagged twice, by `shared_website` *and* `fuzzy_name`. Undoing one of
those does not undo a merge the other still confirms.

### 4.5 The decisions are labelled data

`rejected_distinct` is as valuable an answer as a confirmation. `GET /stats/review` reports, per
detection method:

```jsonc
{ "method": "fuzzy_name", "pending": 22, "confirmed_duplicate": 1, "rejected_distinct": 2,
  "confirm_rate": 0.3333,
  "mean_confidence_confirmed": 1.0, "mean_confidence_rejected": 0.94 }
```

`confirm_rate` is that detector's **observed precision** on pairs a human has actually looked at.
It is the number the `LEADMIND_FUZZY_NAME_THRESHOLD` should be tuned against — labelled data
produced by the review process itself, rather than a threshold picked because 92 sounded strict.
A method nobody has reviewed reports `null`, not `0`: unknown precision is not zero precision.

## 5. Errors

Every failure is RFC 9457 `application/problem+json`. Errors are part of the interface; a client
that gets JSON for a 404, HTML for a 500 and a differently-shaped JSON for a validation failure
has to write three parsers and will write one.

```jsonc
{
  "type": "about:blank#not_found",
  "title": "Not found",
  "status": 404,
  "detail": "lead not found (lead_id='…')",
  "instance": "/api/v1/leads/…",
  "request_id": "c4e48e6326b94aeda5ff77a57928031e"
}
```

| Status | When |
|---|---|
| `404` | The resource does not exist |
| `409` | The decision conflicts with a merge already applied to one of these leads |
| `422` | A parameter was rejected, or `survivor_id` is not one of the pair. `errors[]` names the field |
| `503` | Config file is broken, or the database is unreachable (`/readyz`) |
| `500` | Unhandled. The message goes to the log; the client gets the `request_id` and nothing else |

That last row is deliberate: an unhandled exception's text is as likely to contain a connection
string as anything useful.

## 6. Operations

### 6.1 Request tracing

One `request_id` per request, bound to structlog's contextvars, echoed as `X-Request-ID`, and
included in every error body. An inbound `X-Request-ID` is honoured (length-capped, since it is
attacker-controlled and ends up in log lines) so a trace survives a proxy.

This is the same idea as Phase 1's `run_id` on every ingest log record. A user reporting "it
returned a 500" with that id gives the whole server-side story for free.

```
request_completed  method=GET path=/api/v1/leads query='page_size=1&q=pumo'
                   status_code=200 duration_ms=88.79 request_id=8f58a3be…
```

### 6.2 Liveness and readiness are two endpoints

They answer different questions and a caller acts differently on each.

- `/healthz` — the process is running. If it fails, restart.
- `/readyz` — the process can serve: database reachable **and** `alembic_version` at the head
  this build of the code expects. If it fails, stop sending traffic but do *not* restart. A
  database blip is not a crash loop, and treating it as one turns a two-minute outage into a
  rolling restart storm.

The schema check is the interesting half. Serving against a schema the code was not written for
is how a deploy corrupts data quietly; reporting not-ready lets the operator run the migration.

### 6.3 `X-Rubric-Version`

Every leads response carries the rubric that produced its scores, in a header as well as in each
row, so a client comparing two responses can tell a rescore from a data change.

### 6.4 Configuration

| Variable | Default | |
|---|---|---|
| `LEADMIND_API_PREFIX` | `/api/v1` | |
| `LEADMIND_API_DOCS_ENABLED` | `true` | Turn off in production |
| `LEADMIND_API_CORS_ORIGINS` | *(empty)* | Comma-separated exact origins. Empty means CORS is off |
| `LEADMIND_API_DEFAULT_PAGE_SIZE` | `25` | |
| `LEADMIND_API_MAX_PAGE_SIZE` | `200` | Hard ceiling |

CORS takes exact origins only. `allow_origins=["*"]` with credentials is rejected by browsers
anyway, and a wildcard here would be a default nobody revisits.

## 7. Where the code lives

```
backend/app/
├── api/
│   ├── app.py          application factory, middleware and router wiring
│   ├── deps.py         session dependency, pagination
│   ├── errors.py       RFC 9457 handlers
│   ├── middleware.py   request id, access log
│   └── routers/        leads · companies · duplicates · stats · health
├── schemas/            Pydantic v2 request and response models
└── services/           query building, serialisation, the merge decision
```

The split matters in one direction: **services know nothing about FastAPI**. Routers do HTTP —
parse, validate, serialise, choose a status code. Everything that decides what is *true* — which
leads match a filter, which lead survives a merge, whether a decision conflicts — lives in
`services`, where it can be called from a test, a CLI command or a background job without a
request object. It is also what keeps the routers short enough to read.

Schemas are kept separate from the SQLAlchemy models for a related reason. A schema generated
from the ORM leaks every column the database happens to have — surrogate keys, internal flags,
anything added by tomorrow's migration — into a public interface that then cannot change without
breaking clients.

## 8. Schema change

Migration `5f21ac9d1b64` — *human review and reversible merge*:

- `leads.merged_into_id` / `merged_at` / `merged_by`, with a self-referencing foreign key, an
  index, and a `merged_into_id <> id` check constraint.
- `duplicate_candidates.resolution_note` — the reviewer's prose, in its own column rather than
  mixed into `evidence`, which holds what the detector measured and must stay reproducible from
  the same inputs.
- A GIN trigram index on `leads.normalized_name`, because `?q=pumo` compiles to
  `ILIKE '%pumo%'` and a b-tree cannot serve that. `pg_trgm` was already created in schema v1.

## 9. Tests

104 tests were added; the suite is 302.

**Unit — no database.** Pagination arithmetic. The three-state verification semantics. The
decision-request validators. And a set that compiles SQL and inspects it rather than running it:
that merged leads are excluded by default, that every sort ends in the id tiebreak, that a
hostile `sort` value falls back instead of reaching SQL, that search text arrives as a bound
parameter.

**Integration — real PostgreSQL, real workbook.** Each API module ingests the full 2 520 rows
into a transaction that is rolled back at the end. Verification results are *seeded*
deterministically rather than measured: real verification needs DNS and HTTP, which a test must
not, but a filter reading `domain_verifications` cannot be tested against a table nobody wrote to
— it would pass by returning nothing, which is exactly the bug it exists to catch.

The corpus fixture is module-scoped rather than session-scoped deliberately. It holds one
long-lived uncommitted transaction; a session-scoped version would still be open when the golden
ingest tests run, and their writes would block on the same unique keys.

Assertions worth naming:

- Paging 8 pages returns 200 distinct leads — no repeats, no gaps.
- A page of 100 costs exactly as many SQL statements as a page of 25.
- Confirming a duplicate leaves the loser's identifiers intact and `stats.leads` down by one;
  undoing restores both.
- `?q=pumo` returns 5, and the company view shows one company with 5 branches and 5 distinct
  inboxes.
- `website_live` is `null` and `measured: false` for a lead with an unverified website, and its
  weight is absent from `weight_available`.
